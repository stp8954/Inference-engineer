# YALM: Building LLM Inference from Scratch — Andrew Chan

- **Type:** Blog post. https://andrewkchan.dev/posts/yalm.html

- **Accessed:** 2026-08-24
- **Coverage:** COMPLETE. Full walkthrough of building Mistral-7B inference in C++ and CUDA without external frameworks.

## Summary

A practical, pedagogical implementation of LLM inference optimization across CPU and GPU, covering the engineering path from naive loops to production-ready performance. Chan builds inference in stages — CPU threading (4.2 tok/s), FP16 quantization with F16C (8.4 tok/s), GPU warp-based matmul (51.7 tok/s), kernel fusion and memory coalescing (63.7 tok/s), attention kernel redesign (63.8 tok/s). Final results match or exceed llama.cpp while maintaining code readability and educational transparency. Each optimization step is explained with concrete numbers, compiler pragmatics, and lessons learned.

## Relevance to the series

**Week 1–3 context:** Demonstrates the concrete engineering constraints that the bandwidth-ceiling math (Week 1) and prefill/decode distinction (Week 2) describe. Shows *why* memory coalescing, kernel fusion, and attention redesign matter once you're actually bound by bandwidth.

**Weeks 5–9 (framework survey):** Case study of a minimalist inference engine with explicit design choices (warp-level matmul, manual kernel fusion, tuned attention) — a reference point for comparing vLLM, TensorRT-LLM, and other production engines later.

**Weeks 25–30 (Rust engine arc):** Direct architectural parallel. Chan's progression (CPU → GPU, naive → optimized, compute-bound → bandwidth-bound) is the same path the Rust engine will take. His attention kernel redesign and memory coalescing strategies are applicable to the Rust implementation.

**Measurement culture:** Echoes the series' philosophy: no black-box benchmarks, visible optimizations with numbers, code is the explanation.

## Key takeaways for future posts

1. FP16 KV cache quantization requires careful attention to compiler behavior — manual unrolling with prefetching can recover 1-2% performance.
2. Attention kernel redesign for memory-coalesced writes is a high-ROI optimization (63.7 → 63.8 tok/s was marginal, but the technique generalizes).
3. CPU baseline (4.2 tok/s on CPU, 63.8 tok/s on GPU) shows why GPU inference became standard — ~15× speedup.
4. Educational code that is readable and incremental (showing each stage) is compatible with shipping correct numbers.

## Appended 2026-08-25 — ingest completed to schema, and two corrections

The 2026-08-24 pass created this stub and a CLAUDE.md bookmark but did not touch the concept and claims
pages the schema requires, and was written from a summary rather than the figures. Completed now.

**Corrections to "Key takeaways" above.** Points 2 and 3 are wrong and are superseded:

- Point 2 attributes 63.7 → 63.8 to the attention kernel redesign. It does not: the **attention redesign is 56.1 → 63.7 tok/s (+13%)**, a large win. The 63.7 → 63.8 step is the FP16 KV cache, which was nearly flat at short context — and *that* is the one whose gain the compiler ate (see point 1).
- Point 3 compares the mid-ladder CPU figure to the final GPU figure. The **best CPU result is 8.2–8.4 tok/s**, not 4.2, so the honest CPU→GPU ratio is **~7.6×**, not ~15×.

**Benchmark contract.** Mistral-7B-Instruct-v0.2, FP16 weights and FP16 KV cache, ~15 GB, 4K context
window. GPU: RTX 4090, 1,008 GB/s. CPU: AMD EPYC 7702P, 204.8 GB/s.

**The result that matters most to this series.** The stated weight-bandwidth ceiling on the 4090 is
**67.1 tok/s** and the finished implementation reaches **63.8 tok/s short-context — about 95% of it**;
`calm` reaches 66.0 (~98%) and llama.cpp 61.0 (~91%). This is the strongest published evidence we have
that Week 1's `bandwidth ÷ weights` formula is *predictive* of achievable performance rather than a
loose upper bound. It does not replace our own 8B/H100 measurement, but it does license presenting the
ceiling as a prediction rather than merely a limit.

**The full ladder** (0.6 → 4.2 → 4.4 → 8.2–8.4 on CPU; 2.9 → 51.7 → 54.1 → 56.1 → 63.7 → 63.8 on GPU)
is recorded in `claims/technique-performance.md`. Its shape is the teaching point: the naive GPU port
is *slower* than the optimized CPU version, and one change — warp-strided matmul instead of one block
per output element — is worth ~18× while everything after it combined is worth about 23%.

**Kernel-level findings** filed to `concepts/attention-kernels.md`: the attention redesign (chunked
sequence partitioning for coalesced value loads, `atomicAdd` into shared rather than global memory,
which also avoids subnormal loss) and the FP16 KV cache regression caused by the compiler unrolling
half-precision loads less aggressively — fixed by manual 16-iteration unrolling with register
prefetch, recovering ~75 µs.

**Long-context erosion:** 63.8 → 58.8 tok/s at 4K, versus `calm`'s 66.0 → 65.7. The KV-traffic term
becoming visible, exactly where the Week 1 derivation says it should.
